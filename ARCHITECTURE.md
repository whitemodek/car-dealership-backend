# Backend автосалона

## Назначение

API для публичного сайта автосалона и рабочего интерфейса сотрудников.
Проект должен демонстрировать законченные бизнес-сценарии, а не только CRUD.
Первая версия реализует перечисленные ниже сценарии. Фактические способы
запуска и эксплуатационные ограничения описаны в README и docs/OPERATIONS.md.

## Первая версия

- Публичный каталог: фильтры, сортировка, пагинация, карточка автомобиля,
  фотографии, характеристики, цена и доступность.
- Управление каталогом: создание черновиков, публикация, снятие с публикации,
  изменение цены с историей изменений.
- Заявки покупателей: покупка, обратный звонок, тест-драйв; назначение менеджера,
  история обработки и допустимые переходы статусов.
- Бронирование конкретного автомобиля: срок действия, отмена, истечение,
  подтверждение сотрудником; защита от одновременных активных броней.
- Сотрудники: вход, завершение сессий, роли администратора и менеджера,
  проверка прав на каждом закрытом endpoint.
- Аудит существенных действий сотрудников.

В первой версии нет приёма платежей, кредитного скоринга, интеграции с 1С,
публичной регистрации покупателей и поддержки независимых автосалонов как SaaS.
Эти функции требуют отдельных требований и интеграционных контрактов.

## Архитектура

Go, PostgreSQL и модульный монолит. Один API-процесс и отдельный режим запуска
фонового обработчика из того же приложения. REST API с контрактом OpenAPI.
Фотографии заранее размещаются в собственном S3/CDN, в БД — HTTPS-ссылки.
Прямые бинарные загрузки и выдача presigned upload URL в эту версию не входят.
Redis добавляется только при установленной потребности, например для общего
ограничения запросов при нескольких экземплярах API.

Предлагаемая структура:

```text
backend/
  cmd/api/             сборка и запуск HTTP-сервера
  cmd/worker/          обработка фоновых задач
  internal/
    platform/          конфигурация, БД, HTTP, логи, время
    identity/          сотрудники, роли, сессии
    inventory/         автомобили, публикация, цены, медиа
    leads/             обращения и их обработка
    reservations/      бронирование и истечение
    audit/             журнал действий
    database/          пул, runner, migrations/ и fixtures/
  tests/integration/   проверки с настоящим PostgreSQL
api/openapi.yaml       контракт API
deploy/                локальная среда и настройки развёртывания
```

Модули владеют своими бизнес-правилами. HTTP-обработчики разбирают запрос,
вызывают сценарий и формируют ответ. SQL и границы транзакций находятся в слое
хранения. Интерфейсы вводятся на нужных границах, а не для каждой структуры.
SQL-запросы явные и параметризованные, реализованы на pgx. Генератор sqlc пока
не используется; соответствие схемы и запросов проверяют интеграционные тесты.

## Ключевые правила данных

- Модель/комплектация и конкретный автомобиль — разные сущности. Бронирование
  относится к конкретному экземпляру. Для автомобилей с пробегом существенны
  пробег, состояние и история. Выбран единый каталог новых автомобилей и
  автомобилей с пробегом, с явным признаком new/used и правилами для каждого типа.
- Деньги хранятся целым числом минимальных денежных единиц с кодом валюты.
  Цены не используют float. Правила налогов и отображения цены согласуются отдельно.
- Время хранится как timestamptz; API передаёт даты с явным часовым поясом.
- Состояние публикации отделено от состояния автомобиля: черновик карточки
  не является состоянием продажи.
- Проданный или снятый с продажи автомобиль нельзя забронировать.
- Создание брони сериализуется блокировкой строки автомобиля в транзакции:
  сначала закрываются истёкшие брони, затем проверяется и создаётся новая.
  Частичный уникальный индекс защищает от двух броней в активном статусе.
  Само наступление времени не изменяет индекс: истечение также обрабатывает worker.
- Истечение проверяется в момент действия, поэтому задержка worker не делает
  просроченную бронь действительной.
- Создание брони поддерживает ключ идемпотентности; одинаковый ключ с другим
  содержимым запроса возвращает конфликт. Данные ключа и бронь сохраняются атомарно.
- Изменение статуса и запись аудита выполняются в одной транзакции.
- Уведомления создаются через transactional outbox. Доставка может повторяться;
  обработчики должны выдерживать повторную обработку.
- Контакты покупателей не публикуются в каталоге и не попадают в обычные логи.
  Срок хранения и удаление персональных данных определяются перед внедрением.

## Безопасность и эксплуатация

- Хеширование паролей современным алгоритмом; токены сессий хранятся в БД
  только в виде хеша, имеют срок действия и могут быть отозваны.
- Сессии передаются в Authorization: Bearer, cookies не используются.
  Для браузерного frontend — хранение в памяти или собственный BFF с защищёнными
  cookie и CSRF; origins задаются явным списком. Токены не хранятся в localStorage.
- Параметры запросов и размер JSON-тела ограничены; ссылки фото проверяются.
  Бинарные загрузки отсутствуют, проверка содержимого файлов относится к S3/CDN pipeline.
- Ограничение частоты входа и публичных заявок; единый безопасный формат ошибок.
- Конфигурация валидируется при запуске; секреты поступают из окружения.
- Структурированные логи, request ID, метрики длительности и ошибок запросов.
- Liveness отдельно от readiness; readiness учитывает доступность PostgreSQL.
- Таймауты HTTP/БД, корректное завершение процесса и остановка фоновых задач.
- Миграции запускаются отдельным шагом развёртывания. Изменения схемы учитывают
  совместимость при обновлении работающих экземпляров.
- Документированные backup/restore и сценарий проверки восстановления в CI
  на отдельной БД, с запуском API на восстановленных данных.

## Порядок реализации и приёмка

1. Основа: конфигурация, сервер, health endpoints, ошибки, логи, PostgreSQL,
   миграции, Docker Compose и CI. Чистая среда запускается по README.
2. Каталог: схема для новых автомобилей и автомобилей с пробегом, публичные чтения, фильтры и
   публикация; интеграционные тесты запросов, пагинации и ограничений данных.
3. Сотрудники: сессии и роли; тесты запрета доступа, отзыва и истечения сессий.
   Управление каталогом подключается только с проверкой прав.
4. Заявки: создание и обработка; тесты валидации, прав и переходов статусов.
5. Брони: транзакции, идемпотентность, worker; конкурентный тест доказывает,
   что из нескольких одновременных запросов только один создаёт активную бронь.
6. Подготовка к демонстрации: OpenAPI, демонстрационные данные, полный сценарий
   «публикация → заявка → бронь → продажа», проверка восстановления и нагрузочный
   отчёт с описанием оборудования, нагрузки и измеренных результатов.

Каждый этап оставляет работающий результат. CI выполняет форматирование,
go vet, unit-тесты и интеграционные тесты; race detector запускается на Linux.
Не следует заявлять производительность или готовность к внедрению без измерений.

## Что нужно определить перед внедрением

Формат автосалона и филиалы, правила бронирования, валюты и налоги,
интеграции, ожидаемая нагрузка, требования к персональным данным,
целевые сроки восстановления и допустимая потеря данных. Прохождение тестов
само по себе не заменяет проверку этих требований в целевом окружении.
