# Эксплуатация

## Развёртывание

compose.yaml предназначен для локальной разработки. API и PostgreSQL публикуют
порты только на loopback. В production используйте собственные secret manager,
сертификаты и reverse proxy; задайте APP_ENV=production и DATABASE_URL с
sslmode=verify-full. PostgreSQL должен иметь настроенный TLS и доверенный CA.
Если CA частный, смонтируйте его и задайте sslrootcert в URL соединения.

Контейнер приложения работает непривилегированным пользователем. Миграции —
отдельная операция, не побочный эффект старта каждой реплики. Миграционный
пользователь должен иметь DDL-права; API/worker используйте с отдельными
ролями и минимальными DML-правами на соответствующие таблицы. Пул каждой
реплики ограничен 20 соединениями; учитывайте суммарное количество реплик.

Новые миграции добавляются новым файлом. Применённые файлы нельзя менять:
контрольная сумма проверяется. Миграции сериализуются advisory lock и применяются
атомарно. Обратные миграции намеренно не выполняются автоматически; для опасных
изменений нужны отдельный план восстановления и проверенная резервная копия.

При обновлении изображения повторно запустите миграции, затем обновите API и
worker. Изменения схемы должны оставаться совместимыми с предыдущими репликами
на время обновления. SIGTERM завершает API с ожиданием активных запросов.

## Наблюдение

- `/health/live` — процесс принимает запросы.
- `/health/ready` — доступна БД с применённой схемой. При отказе БД ответ 503.
- `/api/v1/admin/metrics` — счётчики текущего процесса, соединения БД, pending
  и failed outbox. Endpoint требует сессию администратора; внешняя система
  мониторинга должна обновлять свою сессию. Счётчики сбрасываются при перезапуске.
- JSON-логи включают route pattern, статус, длительность и request ID, исключают
  тела, query strings, пароли, токены и контакты. Защищайте доступ и к самим логам.

Отслеживайте рост ошибок 5xx, длительности запросов, очередь outbox, отсутствующий
worker, истечение сертификатов и свободное место БД. Полноценные SLO и алерты
задаются для целевого окружения; встроенные метрики не являются готовой
инфраструктурой мониторинга.

## Уведомления

Если WEBHOOK_URL не задан, worker продолжает закрывать брони, а события остаются
pending. Это видно в метриках и логе запуска. Для доставки нужен HTTPS endpoint
и WEBHOOK_SECRET (случайный ключ минимум 32 байта).

Payload: `id`, `kind`, `entity_id`, `created_at`. Контактов в payload нет.
Получатель, которому нужны детали заявки, получает их отдельно через API
сотрудников с соответствующими правами.

Заголовки:

- `X-Event-ID`: уникальный ID события, ключ дедупликации у получателя.
- `X-Webhook-Timestamp`: Unix timestamp.
- `X-Webhook-Signature`: `sha256=` + hex HMAC-SHA256 от `timestamp + "." + raw_body`.

Получатель проверяет timestamp (например, допускает 5 минут), сравнивает подпись
в постоянном времени и дедуплицирует ID. Доставка — как минимум один раз:
сбой между HTTP-ответом и фиксацией в БД может привести к повтору.
2xx подтверждает доставку. Редиректы не выполняются; остальные статусы вызывают
повторы с экспоненциальной задержкой. После восьми неудачных попыток событие
попадает в failed. Lease — две минуты, позволяет несколько worker.

Для повторной доставки после устранения причины оператор БД может адресно
сбросить failed_at и attempts, установить available_at=now(). Не меняйте ID:
получатель должен сохранить дедупликацию. Успешные события удаляются через 30
дней; недоставленные события сохраняются. Контакты и аудит автоматически не
удаляются: срок хранения и процесс обработки запросов на удаление должны быть
согласованы до production.

## Ограничения запросов

Общий PostgreSQL limiter поддерживает несколько реплик API: login — 25 запросов
на IP и 10 на email в минуту, заявки — 10 на IP, брони — 20 на IP. Это фиксированные
минутные окна. Ключи хешируются; старые окна удаляет worker.

По умолчанию API использует RemoteAddr и игнорирует X-Forwarded-For. За reverse
proxy задайте TRUSTED_PROXY_CIDRS только для фактических proxy-адресов/подсетей.
Заголовок обрабатывается справа налево до первого недоверенного адреса. Proxy
должен перезаписывать либо правильно дополнять цепочку, а прямой доступ к API
обходя proxy должен быть закрыт сетевыми правилами. Без такой настройки все
клиенты proxy могут попадать в лимит одного адреса. Доверие 0.0.0.0/0 или ::/0
запрещено проверкой конфигурации.

## Резервное копирование и восстановление

Используйте pg_dump/pg_restore совместимой версии. Запускайте задания из
защищённого окружения и шифруйте резервные копии: в них есть контакты и хеши
паролей. Для production установите собственные RPO/RTO и политику WAL/PITR.

Пример Bash для локальной среды:

```sh
docker compose exec -T db pg_dump -U dealership -d dealership -Fc > dealership.dump
docker compose exec -T db createdb -U dealership dealership_restore_check
docker compose exec -T db pg_restore -U dealership -d dealership_restore_check --exit-on-error < dealership.dump
docker compose exec -T db psql -U dealership -d dealership_restore_check -c 'SELECT count(*) FROM cars; SELECT count(*) FROM schema_migrations;'
```

Проверка проводится в отдельной новой БД. Затем запустите API на восстановленной
БД и проверьте чтения и сценарий продажи. Не восстанавливайте поверх рабочего
каталога. Бинарный dump перенаправляйте из Bash или PowerShell 7.4+; старый
PowerShell может изменить бинарный поток.

Для S3/CDN настройте отдельное резервирование объектов и доступность публичных
HTTPS-ссылок. Восстановление PostgreSQL само по себе не восстанавливает фотографии.

## Границы версии

Нет приёма платежей, кредитования, интеграции с DMS/1С, мультитенантности,
автоматического удаления персональных данных, встроенного TLS и управления
сертификатами, прямых бинарных загрузок в S3 и полноценной системы мониторинга.
Это законченный API первой версии; внедрение требует настройки перечисленных
процессов под условия конкретного автосалона.
