# Нагрузочная проверка

## Локальный HTTP smoke-тест

Измерение выполнено 6 октября 2026 года, Windows amd64, Go 1.26.8,
PostgreSQL 17.11 в переносимом локальном процессе. CPU: AMD Ryzen 5 5600,
6 ядер / 12 потоков; доступная физическая RAM: 15.9 GiB. API и БД на одной машине;
HTTP использует loopback и keep-alive, без TLS/reverse proxy. Каталог содержит
100 машин. Каждый ответ возвращает 20 машин с сортировкой по цене в RUB.
Логи направлены в io.Discard, метрики и middleware работают.

Результат одного запуска:

| Показатель | Значение |
| --- | --- |
| Запросы | 400 |
| Параллельные клиенты | 8 |
| Время выполнения | 185 ms |
| p50 | 1.605 ms |
| p95 | 2.496 ms |
| p99 | 92.274 ms |
| Ошибки HTTP/БД | 0 |

Это короткая проверка корректности под нагрузкой на прогретой небольшой БД.
Она не измеряет предел производительности, не включает большие фотографии,
логирование на диск, TLS, WAN, фоновую работу и длительный стабильный поток.
Высокий p99 относительно p95 показывает влияние начальных соединений и
планирования процессов; для выводов о capacity нужен длительный сценарий.
Для сравнения с другими окружениями нужно повторить сценарий с одинаковыми
данными и длительностью, учитывая отличия аппаратуры и фоновой нагрузки.

## Воспроизведение

```sh
# Сначала передайте TEST_DATABASE_URL для тестовой БД из защищённого окружения.
LOAD_TEST=1 go test -count=1 -run TestCatalogLoad -v ./backend/tests/integration
```

Тест создаёт собственную случайную схему, заполняет каталог, запускает HTTP
сервер, выполняет запросы и очищает только свою схему. Используйте тестовую БД.

Отдельные интеграционные проверки запускают 16 одновременных бронирований
одной машины (успех ровно один) и восемь повторов одного idempotency key
(одна бронь). Это проверки инвариантов, а не throughput бронирования.

## Перед запуском production

На целевом оборудовании зафиксируйте CPU/RAM, версии, количество API/worker
реплик, параметры БД и реальный объём каталога. Выполните продолжительные
сценарии чтения, поиска, заявок и конкурентного бронирования с настоящим
логированием и TLS. Измерьте p50/p95/p99, ошибки, очереди, CPU, память,
соединения и планы SQL; проверьте деградацию при отказах БД и получателя webhooks.
SLO и лимиты нагрузки устанавливаются по этим измерениям.
